### Installation guidance

- **n8n Cloud:** no local Node.js install is needed; create/import workflows in the hosted instance.
- **Self-hosted n8n:** install a supported n8n release using the official n8n installation method. The collection guide's example is local n8n `2.42.7`, not a guaranteed minimum.
- **Database:** create a Supabase project, then execute the SQL scripts in the order documented in `README.md`.
- **Python:** do not run `pip install` for this project based on the supplied files. If future repository files introduce Python scripts, inspect those scripts and their own dependency declarations before adding packages.

## 4. Database and SQL prerequisites

Use the SQL files included in the supplied archives. Do not recreate these tables by guessing their definitions.

### SQL scripts

| Order | File path inside source ZIP | Purpose |
|---|---|---|
| 1 | `collection_workflow/scripts/raw_tables.sql` (same intended raw contract as `Cleaning_Transformation_Package/sql/01_raw_tables.sql`) | Creates `raw` schema and nine raw landing tables. All source data columns are text to preserve malformed values; API tables include `raw_record jsonb`. |
| 2 | `collection_workflow/n8n/ops_tables.sql` (or `Cleaning_Transformation_Package/sql/02_ops_tables.sql`) | Creates `ops.agent_logs`, `ops.data_contracts`; the cleaning package version adds `ops.data_contracts.profile jsonb`. Prefer the cleaning package version for the end-to-end setup. |
| 3 | `Cleaning_Transformation_Package/sql/03_clean_tables.sql` | Creates `clean` typed output tables, `cleaning` helper schema/functions, and ops tables for rules, approvals, and quarantine. |
| 4 | `Cleaning_Transformation_Package/sql/04_transform_tables.sql` | Creates transformation/model schemas and tables, roles/grants, validation/publishing functions, `ops.transform_models`, `analytics.refresh_status`, and indexes. |
| 5 | `explain_phase/scripts/insights_tables.sql` | Creates `insights` schema/config and analytics insight/fact/staging tables, indexes, and grants. Run after transformation schema is installed; verify the database owner can create required objects. |

**Important:** `01_raw_tables.sql` and the collection `scripts/raw_tables.sql` are overlapping definitions. Run one of them, not both as competing sources of truth. For the complete pipeline, use `Cleaning_Transformation_Package/sql/01_raw_tables.sql`, which matches the downstream cleaning contract, and use `Cleaning_Transformation_Package/sql/02_ops_tables.sql` rather than the collection-only `ops_tables.sql`. Both packages are idempotent in many places, but that is not a substitute for a planned migration.

### Database schemas and table contracts

| Schema | Tables / objects | Contract |
|---|---|---|
| `raw` | `orders_csv`, `order_items_csv`, `customers_csv`, `sellers_csv`, `geolocation_csv`, `products_sheet`, `category_translation_sheet`, `payments_api`, `reviews_api` | Landing zone. Preserve source values as text, with load metadata (`_run_id`, `_loaded_at`) and untouched API JSON in `raw_record` where defined. |
| `cleaning` | Helpers such as `try_numeric`, `try_timestamp`; dynamic working copies `cleaning.<source>` | Temporary/rebuildable work area for profiling, dry runs, and generated cleaning SQL. Do not treat as published analytics. |
| `clean` | `orders`, `order_items`, `customers`, `sellers`, `geolocation`, `products`, `category_translation`, `payments`, `reviews` | Typed and cleaned data consumed by transformations. See `docs/CLEANING.md` and `sql/03_clean_tables.sql` for full column definitions. |
| `ops` | `agent_logs`, `data_contracts`, `cleaning_rules`, `cleaning_approvals`, `quarantine`, `transform_models`; plus explain workflow's writes to logs | Run logs, data contracts/profiles, human decisions, quarantined records, validated SQL history and statuses. Keep the versions/columns in the SQL scripts aligned. |
| `models` | One validated view per transformation question | AI-generated SQL is created/validated here under the restricted `transform_agent` role. |
| `analytics` | `orders_wide`, `order_items_wide`, `kpi_summary`, `monthly_revenue`, `revenue_by_state`, `top_categories`, `refresh_status`, `order_facts`, `insight_summary`, `insight_causes`, `insight_recommendations` | Published tables consumed by Metabase and the Explain stage. Some objects are created by different SQL scripts and workflows. |
| `insights` | `kpi_config`, `stage_summary`, `stage_causes`, `stage_recommendations` and SQL helper routines | Human-maintained KPI configuration and staging for Explain output before publication. |

No extension creation is present in the supplied SQL scripts; no PostgreSQL extension is explicitly required by the inspected files. Do not enable an extension unless a deployment-specific check demonstrates a need.

### Roles and permissions

`04_transform_tables.sql` refers to database roles `transform_agent` and `analytics_reader`, and grants restricted permissions to them. It includes `grant transform_agent to current_user`, grants access to `clean`, and limits the AI role to creating views in `models` rather than directly publishing to `analytics`. It also grants the reader role select access to analytics objects and selected operational status/log objects.

Before running this SQL:
1. Review the script's role creation and grant statements in your Supabase environment.
2. Confirm the executing database role has permission to create/alter roles and grant memberships. Supabase's managed-role constraints may require an owner/admin to adapt the SQL.
3. Do not simply grant the AI agent or dashboard account database-owner/superuser privileges to bypass permission errors.
4. If a role already exists, inspect its privileges rather than assuming it is configured safely.

### Data volumes and preservation

- Collection sources described in the included guide: five CSV files (orders, order items, customers, sellers, geolocation), two Google Sheet tabs (products, category translation), and two paginated JSON API sources (payments, reviews).
- The source guide reports approximately 1,002,183 geolocation rows, 104,406 payments, and 99,544 reviews; counts may differ if datasets are regenerated.
- Raw tables intentionally retain dirty values and repeated headers/blank rows so cleaning can detect them.
- Do not upload `answer_key.csv` to Google Drive or any source folder read by the pipeline.

## 7. Source integrations and configuration parameters

### Google Drive / Google Sheets

- Upload the five CSV sources to a dedicated Drive folder and record each file ID.
- Create one spreadsheet with tabs exactly `products` and `category_translation`; record its spreadsheet ID.
- Preserve values as text during import. The guide specifically warns against converting strings such as decimal-comma values or leading-zero ZIP prefixes into numbers/dates.
- In `Collection · Main` → `Sources` Code node, replace each `DRIVE_FILE_IDS` `PASTE_ID`, and `SPREADSHEET_ID` `PASTE_ID`.
- Reconnect Google Drive and Google Sheets credentials on their nodes.

### Mock API and webhooks

- Workflow: `Mock API · Olist payments & reviews`, path `olist-mock-api`, GET webhook, response node.
- Collection `Sources` node defaults `MOCK_API_URL` to `http://localhost:5678/webhook/olist-mock-api`.
- This URL only works if the mock API workflow is published and reachable from the HTTP Request node's runtime. `localhost` means the n8n host/container itself; it does not mean the user's browser or another container.
- If n8n is containerized or remote, replace it with a reachable host/service URL. Do not put a `/webhook-test/` URL in the collection source settings for normal runs.
- API pagination is configured using query parameter `page`, with a maximum of 50 requests; the response contract includes `page`, `total_pages`, and `data`. Verify the mock API response matches the loader's expected data shape before full load.

### Collection `Sources` Code node

Observed configurable values:
- `DRIVE_FILE_IDS`: `orders`, `order_items`, `customers`, `sellers`, `geolocation`
- `SPREADSHEET_ID`
- `MOCK_API_URL`
- `ONLY`: empty means all nine sources; use a short list for safe tests
- `batch_size`: default 2,000 rows; geolocation explicitly uses 5,000
- source mapping includes `category_translation_sheet`, `sellers_csv`, `products_sheet`, `customers_csv`, `orders_csv`, `order_items_csv`, `payments_api`, `reviews_api`, and `geolocation_csv`.

### Cleaning workflow settings

In `Cleaning · Main` → `Tables` Code node:
- `ONLY`: empty means all cleaning sources; can be set to one source such as `['sellers']` for a test.
- `FRESH_RULES`: false by default; true forces new rule proposals rather than reuse of saved rules.
- `APPROVAL_FORM_URL`: must be checked and configured for your n8n instance if the approval link/form URL is environment-specific.
- The workflow waits up to 2 hours for approval. Undecided rules are expired/rejected by the workflow logic; understand the consequences before production use.

### Transformation workflow settings

In `Transformation · Main` → `Questions` Code node:
- `ONLY`: empty means all configured views; can be set to a small list such as `['kpi_summary']`.
- `FRESH_SQL`: false by default; true asks the model for fresh SQL instead of reusing a previously passed definition.
- A nightly Schedule Trigger is configured for cron `0 2 * * *` (02:00 in the n8n runtime's timezone). It is not automatically active merely because it exists in the JSON; enable/publish only after manual tests.

### Explain workflow settings

In Explain workflow → `Settings` Code node:
- `MONTHS`: empty means all months with a movement; can be set e.g. `['2018-03']` for a targeted run.
- `KPIS`: empty means all enabled KPIs in `insights.kpi_config`.
- Explain uses a staging-and-publish pattern: stage results are reconciled/validated before final publication. Do not bypass its checks.

### Metabase environment example

`explain_phase/metabase/dashboard.env.example` is included in the Explain ZIP. It names `MB_URL`, `MB_ADMIN_EMAIL`, `MB_ADMIN_PASSWORD`, optional `MB_DATABASE`, and PostgreSQL connection values `PG_HOST`, `PG_PORT`, `PG_DB`, `PG_USER`, `PG_PASSWORD`. Use placeholders and a private `.env` file; do not commit secrets. The referenced `scripts/build_metabase_dashboard.py` is not included in the supplied archives, so the template alone cannot run that builder; create the dashboard manually using `metabase/DASHBOARD.md` or obtain the missing script separately.
