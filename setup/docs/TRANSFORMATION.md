# Transformation workflow: how it works and how to set it up

The transformation stage (Milestone 4, FR-T1 to FR-T5) turns plain-English business questions into SQL, checks it, and stores the results as **tables** in the `analytics` schema. The transformation agent writes the SQL, and fixed guardrails and validation queries decide whether it goes live. Every SQL is logged.

Metabase and the chat Q&A read only those tables. The pipeline can run at night, and in the morning the dashboard opens straight away on the last good run, without waiting for any workflow.

| Workflow | ID | File | Started by |
|---|---|---|---|
| Transformation · Main | `olistTransMain01` | `n8n/transformation_main.json` | **You** (Execute workflow), the `Every night` trigger, or later the Week 3 orchestrator |

Generated by `python -I scripts/build_transformation_workflow.py`.

## 1. The idea in one picture

```
            per question                                                     after ALL questions passed
Questions ──▶ Transformation agent ──SELECT──▶ Check SQL ──▶ one transaction:            ──▶ Publish tables (one transaction)
(question,    (question + columns +            (guardrails,   SET LOCAL ROLE transform_agent     models.<view> ──copy──▶ analytics.<view>
 columns,      definitions + schema;            no AI)        create view models.<view>          + indexes, + refresh_status
 reference SQL) never sees the answer key)                    transform.validate_view(...)                       │
                                                                     │ fail                          Metabase / chat read analytics.*
                         Repair agent ◀── its SQL + why it failed ◀──┘
                              │
                              └──▶ same checks ──fail again──▶ log, STOP: nothing is published (FR-T4)
```

Two schemas, two jobs:

| Schema | Holds | Who writes | Who reads |
|---|---|---|---|
| `models` | one **view** per question: the agent's validated SQL | the agent's SQL, as role `transform_agent` | the publish step |
| `analytics` | one **table** per question, plus `refresh_status` | only the publish step | Metabase, chat Q&A (role `analytics_reader`) |

Five things keep this reliable:

1. **The agent only writes a SELECT.** *Check SQL* refuses anything else: more than one statement, comments, writing keywords, any schema but `clean`, system functions.
2. **The SQL runs as a restricted role.** `transform_agent` can only read `clean.*` and create views in `models`.
3. **The checks decide, not the AI.** `transform.validate_view` compares each view with a **hand-written reference query** (the answer key in *Questions*) and with the revenue in the clean tables.
4. **All or nothing.** Tables are published only when every view passed, and all in one transaction. If one view fails, the dashboard keeps showing the previous complete run, never a mix of old and new numbers.
5. **Fast reads.** The joins are done once, at night. Metabase filters ready-made, indexed tables.

## 2. One run, step by step

| Step | Node | What happens |
|---|---|---|
| 1 | `Get stored SQL` → `Build prompt` → `SQL needed?` | If the view has SQL that passed before and the question hasn't changed, it is reused: no AI call. Set `FRESH_SQL = true` in `Questions` to ask again. |
| 2 | `Get schema`, `Build prompt` | The prompt gets the question, the required columns, the business definitions, the live `clean` schema and how the tables link. No data rows, and never the reference SQL. |
| 3 | `Transformation agent` | FR-T1. Returns `select_sql`, a plain `explanation` and its `assumptions`. |
| 4 | `Check SQL` | Guardrails. A failure turns into an error in the next step, so nothing runs. |
| 5 | `Create and validate view` | FR-T2, FR-T3. Creates `models.<view>` as `transform_agent` and runs the checks below. |
| 6 | `Read result` → `Save attempt` | FR-T5. The SQL, explanation and every check go into `ops.transform_models` and `ops.agent_logs`, whether it passed or not. |
| 7 | `Repair prompt` → `Repair agent` → … | If it failed: one more try, with the rejected SQL, the failed checks and up to 3 rows that differ from the expected result. |
| 8 | `Fixed?` → `Stop run` | FR-T4. Fails twice → a `failed` run_complete row, the workflow stops with an error, and **nothing is published**. |
| 9 | `Build publish SQL` → `Publish tables` | Every view passed: in one transaction, each `models.<view>` is copied into `analytics.<view>`. The table is emptied and refilled, not dropped, so Metabase's saved questions keep working. It is rebuilt only if its columns changed. Then its indexes are added and `analytics.refresh_status` is updated. |
| 10 | `Run summary` → `Log run` | Final log row with the validated views and the published row counts. |

### Checks (`transform.validate_view`)

| Check | Passes when |
|---|---|
| columns | exactly the columns asked for, with matching types (any number type counts as a number, date and timestamp as time) |
| row count | at least 1 row |
| no duplicate keys / one row | one row per grain value (`kpi_summary`: exactly one row) |
| revenue reconciles | the revenue column adds up to the revenue in the clean tables (rounding tolerance 0.005 per row) |
| matches reference | same rows and values as the hand-written reference SQL (numbers within 0.011) |

## 3. The tables

Business definitions, shared by every table and stated to the agent:

- **Counted order:** `order_status` is not null and not `canceled` or `unavailable`, and the order has at least one item. Every table contains only counted orders.
- **Revenue:** `coalesce(price, 0) + coalesce(freight_value, 0)` over the items of counted orders.
- **orders:** distinct counted orders. **customers:** distinct `customer_unique_id`.
- **avg_order_value:** revenue / orders. Money and averages are rounded to 2 decimals at the end.

**Wide tables** (joined once, for filtering and drill-down in Metabase):

| Table | One row per | Columns | Indexed on |
|---|---|---|---|
| `analytics.orders_wide` | order | order_id, customer_unique_id, customer_city, customer_state, order_status, purchase_timestamp, purchase_month, delivered_timestamp, estimated_delivery_date, delivery_days, is_late, items, revenue, payment_value, main_payment_type, review_score | purchase_month, customer_state, order_status |
| `analytics.order_items_wide` | order item | order_id, order_item_id, purchase_month, customer_state, product_id, category, seller_id, seller_state, price, freight_value, revenue | purchase_month, customer_state, category, seller_id, order_id |

**Summary tables** (ready for the dashboard tiles and charts):

| Table | One row per | Columns | Dashboard |
|---|---|---|---|
| `analytics.kpi_summary` | – (one row) | revenue, orders, customers, avg_order_value, avg_review_score | KPI tiles |
| `analytics.monthly_revenue` | month | month, orders, revenue, avg_order_value | revenue trend |
| `analytics.revenue_by_state` | customer_state | customer_state, orders, customers, revenue | state breakdown |
| `analytics.top_categories` | category | category, items_sold, orders, revenue, revenue_rank | top products (`revenue_rank <= 10`) |

**`analytics.refresh_status`** has one row per table: `row_count`, `run_id` and `refreshed_at`. Put `max(refreshed_at)` on the dashboard as "Data as of …".

Things to know about the numbers:

- Use the summary tables for the fixed tiles and charts, and the wide tables for questions with filters (a state, a category, a month range). Both come from the same definitions and are checked against the same revenue total, so they always agree.
- Orders without a purchase date have a null `purchase_month` and are left out of `monthly_revenue`. If the approver **rejects** `parse_date` on `order_purchase_timestamp` in cleaning, about 14,000 orders drop out of the trend (they still count everywhere else). That is a good demo moment to explain.
- Orders whose customer was quarantined in cleaning are kept, with `customer_state` null, so the states still add up to the total.
- **Adding a table:** add one entry to `questions` in the `Questions` node (view, question, columns, grain, indexes, reference SQL, reconcile). No new nodes are needed.

## 4. Setup

1. **Supabase:** run `scripts/transform_tables.sql` once in the SQL editor, after `clean_tables.sql`. It creates the schemas `models`, `analytics` and `transform`, the roles `transform_agent` and `analytics_reader`, three join indexes on `clean.*`, the validation and publish functions, `analytics.refresh_status` and `ops.transform_models`. It is safe to run again, including over the earlier views-only version, whose `analytics` views are replaced by tables on the first publish.
2. **Import** `transformation_main.json` (n8n stopped, as in section 6 of `n8n/README.md`, or through the editor).
3. **Credentials:**

   | Postgres (`Supabase`) | Gemini (LLM) |
   |---|---|
   | Get stored SQL, Get schema, Create and validate view, Save attempt, Create and validate again, Save retry, Log failure, Publish tables, Run summary, Log run | Transformation model, Repair model |

4. **Run:** run collection and cleaning first, then open `Transformation · Main` → *Execute workflow*. To test one table, set `ONLY = ['kpi_summary']` in `Questions` (only that table is published).
5. **Read-only login for Metabase and the chat:** in the SQL editor, run
   `create role metabase_reader login password '…' in role analytics_reader;`
   and connect Metabase with user `metabase_reader.<project-ref>` through the Session pooler. It can read `analytics.*` and `ops.agent_logs` (for the activity panel), and nothing else: not `models`, `clean` or `raw`.

### Running at night

- **Week 3 (the plan):** the orchestrator runs collection → cleaning → transformation on a schedule. Transformation is the last stage, so the dashboard updates once the whole chain has succeeded.
- **Before that:** enable the `Every night` node (02:00, disabled by default) and **publish** the workflow. It then re-runs transformation on whatever `clean.*` holds.
- **Cleaning at night:** the cleaning run reuses its stored rules, so normally there is no form to answer. If it proposes new risky rules, it waits up to 2 hours for the approver and then treats them as rejected. Keep `FRESH_RULES = false` for scheduled runs.

Quick checks:

```sql
-- when the dashboard data was published
select * from analytics.refresh_status order by table_name;

-- what happened in the last run
select action, source, status, rows_written, reason
from ops.agent_logs where agent = 'transformation' order by logged_at desc limit 20;

-- every SQL the agent wrote and whether it passed
select view_name, attempt, origin, status, error, select_sql
from ops.transform_models order by created_at desc;
```

## 5. Things to watch

- **Re-runs are cheap:** stored SQL is reused (no AI call) but validated again on the current clean data, so a cleaning change that breaks a table is still caught before it reaches the dashboard. Use `FRESH_SQL = true` to show the agent live.
- **Planting a failure for the demo (M7):** set `FRESH_SQL = true` and change a definition in the reference SQL only. The checks reject the agent's view, nothing is published, and the dashboard and `refresh_status` still show the previous run.
- **Publishing locks the tables briefly:** emptying and refilling happen in one transaction. A dashboard opened during those seconds waits for it to finish and then sees the new data, which is no problem at night.
- **Don't edit `analytics` tables by hand:** every publish replaces their contents. Put your own Metabase models or SQL questions on top of them instead.
- **Keep the definitions in one place:** the reference SQL and the agent's instructions both come from `Questions`. If the business changes a definition, change it there. The stored SQL is then rebuilt automatically, because the question's hash changes.
