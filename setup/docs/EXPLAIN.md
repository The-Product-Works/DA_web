# Explain workflow: how it works and how to set it up

`Explain · Main` turns the dashboard from *what* into *why*. It finds the months in which a KPI moved against a normal month, breaks the KPI down by every approved column, and asks the Explain agent for three things: what happened, what caused it and what to do about it. The agent decides **what** the cause is. A fixed SQL query decides **how much** it matters. The agent never runs SQL and never writes a number.

It follows the KPI_insight pattern (SDLC_Insights): people own the SQL, the agent only reads totals, each cause is a filter, and SQL sizes each cause.

| Piece | Where |
|---|---|
| Workflow | `n8n/explain_main.json`, generated by `scripts/build_explain_workflow.py` |
| Tables and functions | `scripts/insights_tables.sql` (schema `insights`, tables `analytics.order_facts` and `analytics.insight_*`) |
| Dashboard cards | `scripts/build_metabase_dashboard.py`: *What happened*, *Why it happened*, *What to do*, *Ruled out*, and the drill-down dashboard |
| First KPI | late delivery rate. Review score and orders/revenue can be added later as rows in `insights.kpi_config` |

## 1. The idea in one picture

```
analytics.orders_wide + order_items_wide (+ two dates from clean.*)
        │ insights.refresh_order_facts()
        ▼
analytics.order_facts ── one row per order: states, cross_state, seller_shipped_late, category, seller, is_late, review
        │
        │ insights.kpi_months()      month vs normal month (median of the 3 months before) → months that moved
        │ insights.breakdowns()      the KPI by every approved column and pair: totals only
        ▼
  Explain agent (Gemini) ── what_happened · ruled_out · causes (filters on approved columns) · recommendations (levers)
        │                    placeholders instead of numbers
        ▼
  checks + insights.size_cause() ── each cause measured: late orders, rate vs normal, points and stars recovered
        │                           bad items: one repair try, then dropped · month must reconcile, else stop
        ▼
  insights.stage_* ──► insights.publish() ──► analytics.insight_summary / insight_causes / insight_recommendations
                                                    │
                                                    ▼
                               Metabase: What happened · Why · What to do · drill-down (opened from the cause filter)
```

## 2. One run, step by step

| Step | Node(s) | AI? | What happens |
|---|---|---|---|
| 1 | *Settings* | – | `MONTHS` (e.g. `['2018-03']`, empty = every month that moved) and `KPIS` (empty = every enabled KPI) |
| 2 | *Refresh order facts* | – | Rebuilds `analytics.order_facts` and clears staging rows left by a run that stopped |
| 3 | *Find moved months* | – | A month moved when its rate is **≥ 1.5×** its baseline **and ≥ 2 points** above it, with ≥ 100 late orders and ≥ 500 counted orders. On the original Olist data: Apr 2017, Nov 2017, Dec 2017, Feb 2018, Mar 2018 and Aug 2018 |
| 4 | *Run breakdowns* | – | Every approved column, plus the pairs `cross_state × seller_shipped_late` and `seller_state × customer_state`. For each value: orders, late orders, the rate, the same orders' rate in a normal month, the value's share of the month's late orders, and the late orders above normal. Top 12 rows per breakdown, largest rise first (about 8 KB of text) |
| 5 | *Explain agent* | ✔ | Returns `what_happened`, `ruled_out`, 1–4 `causes` (1–3 conditions each) and 1–2 `recommendations` per cause, each using a lever from the KPI's list |
| 6 | *Check answer* | – | No digits in any text, only allowed placeholders, approved columns and operators, breakdown names that exist, valid levers, actions that close existing causes |
| 7 | *Size causes* → *Read checks* | – | `insights.size_cause` measures every cause. A cause must match late orders and be late more often than in a normal month. The whole month (empty filter) must equal `kpi_months` |
| 8 | *Repair* (once) | ✔ | Only the rejected items are sent back, with the reasons. Items that still fail are dropped and logged |
| 9 | *Build rows* → *Save month* | – | Fills the placeholders with the measured numbers and ranks causes and actions by points recovered. Sets the drill-down columns `f_*` from the cause filter, and stages the rows |
| 10 | *Publish insights* | – | One transaction into `analytics.insight_*`. A full run also removes months that no longer move |

### What the agent may use

| Setting (`insights.kpi_config`) | Late delivery rate |
|---|---|
| Gap order | a delivered order with `is_late` (delivered date after the estimated date, dates only, as in `orders_wide`) |
| Approved columns | `customer_state`, `seller_state`, `cross_state`, `seller_shipped_late`, `multi_seller`, `category`, `seller_id` |
| Levers | `carrier_route`, `seller_dispatch`, `promised_date`, `peak_capacity`, `ship_together`, `listing_quality` |
| Cross-KPI effect | review stars (`review_score`) |

`seller_shipped_late` = the seller handed the parcel to the carrier after the shipping limit (`clean.orders.order_delivered_carrier_date` > `clean.order_items.shipping_limit_date`). It separates seller delays from carrier delays, and that difference decides the action.

### The numbers on a cause

| Column | Meaning |
|---|---|
| `matched_orders`, `gap_orders`, `rate` | The cause's orders this month, how many were late, and their late rate |
| `baseline_rate` | The same orders' median late rate in the 3 months before (the KPI's baseline if they had none) |
| `points_recovered` | How many points the month's late rate drops if these orders were late only at their normal rate |
| `impact_recovered` | Review stars the month gains if those extra late orders had arrived on time (late orders score lower than on-time ones) |

Example from the test run on the original files: March 2018 was 19.0% late against 7.5% normally. The cause *cross_state = yes and seller_shipped_late = no* covers 4,036 orders, 954 of them late (23.6% against 8.3% normally): **8.8 points** and **0.19 stars**. Volume (+8%) and seller handover are ruled out.

### Placeholders

| Where | Placeholders |
|---|---|
| Any text | `{month}` `{month_rate}` `{month_baseline_rate}` `{orders}` `{prev_orders}` `{orders_change}` |
| A cause's explanation, also | `{rate}` `{baseline_rate}` `{matched_orders}` `{gap_orders}` `{share_of_gap}` `{excess_gap_orders}` `{points_recovered}` `{impact_recovered}` |
| A recommendation's action, also | `{points_recovered}` (the largest of the causes it closes) |

## 3. The tables

| Table | One row per | Read by |
|---|---|---|
| `analytics.order_facts` | order | the sizing functions and the drill-down dashboard |
| `analytics.insight_summary` | KPI and month | *What happened* (headline, rate, baseline, status: `explained` / `partly_explained` / `not_explained`) |
| `analytics.insight_causes` | cause or ruled-out factor | *Why it happened*, *Ruled out*. `cause_filter` holds the AI's filter; the `f_*` columns hold its `=` values for the drill-down |
| `analytics.insight_recommendations` | action | *What to do* (lever, action, the causes it fixes, points) |
| `insights.kpi_config` | KPI | the workflow (written by people) |
| `insights.stage_*` | – | rows of a run that hasn't published yet |

All of them are readable by `analytics_reader` (Metabase), except `insights.*`.

## 4. Setup

1. **Supabase:** run `scripts/insights_tables.sql` once in the SQL editor, after `transform_tables.sql`. It can be run before transformation has published anything, and it is safe to run again (it also refreshes the late-rate row of `insights.kpi_config`).
2. **Import** `explain_main.json`.
3. **Credentials:**

   | Postgres (`Supabase`) | Gemini (LLM) |
   |---|---|
   | Refresh order facts, Find moved months, Run breakdowns, Size causes, Size again, Save month, Log failure, Publish insights, Run summary, Log run | Explain model, Repair model |

4. **Run:** collection → cleaning → transformation first, then `Explain · Main` → *Execute workflow*. To try one month, set `MONTHS = ['2018-03']` in *Settings*.
5. **Dashboard:** run `python -I scripts\build_metabase_dashboard.py` again. It adds the insight cards and the drill-down dashboard.

For the webinar, run it beforehand: nothing needs to run live.

Quick checks:

```sql
-- the months and how well they were explained
select month, status, causes, headline from analytics.insight_summary order by month;

-- causes with their size and filter
select month, rank, cause_name, points_recovered, impact_recovered, cause_filter
from analytics.insight_causes where kind = 'cause' order by month, rank;

-- what the agent returned, and anything dropped
select source, status, reason, details -> 'dropped'
from ops.agent_logs where agent = 'insights' order by logged_at desc limit 20;

-- try a filter by hand
select insights.size_cause('late_delivery_rate', '2018-03-01',
  '[{"column": "cross_state", "op": "=", "value": "yes"}, {"column": "seller_shipped_late", "op": "=", "value": "no"}]');
```

## 5. Things to watch

- **Numbers differ slightly from the proposal.** The proposal compared delivery times; the pipeline compares dates (`orders_wide.is_late`). March 2018 is 19.0% here, not 21.4%. The cleaned data will move them a little again.
- **Safety:** the AI's filters become SQL only inside `insights.filter_sql`, on approved columns, with every value quoted (`%I` / `%L`). A filter value like `x'; drop table …` simply matches nothing.
- **Drill-down from a cause** passes only its `=` conditions. A cause with `in` or `!=` opens a wider segment (the month and the other conditions).
- **Repairs every run?** Look at the dropped items in `ops.agent_logs`, then improve the prompt or the KPI's columns. Don't rely on the repair.
- **Adding a KPI:** add a row to `insights.kpi_config` (population, gap condition, columns, pairs, levers, thresholds). The workflow needs no change. The dashboard cards currently assume the late rate.
- **Testing:** the workflow was tested on PGlite with the original Olist files and stubbed agent answers. The scenarios were a first-try pass, a repair, items dropped, the agent failing twice, a reconciliation stop, and one month only. The real Gemini answers and the Metabase click-through have not been run yet.
