# Cleaning workflow: how it works and how to set it up

The cleaning stage (Milestone 3, FR-K1 to FR-K6) reads the nine raw tables that the collection stage filled, finds the problems, proposes fixes, has a person approve the risky ones, and writes typed tables into the `clean` schema. Those tables are the hand-over to the data-out track.

| Workflow | ID | File | Started by |
|---|---|---|---|
| Cleaning · Main | `olistCleanMain01` | `n8n/cleaning_main.json` | **You** (Execute workflow), later the Week 3 orchestrator |
| Cleaning · Approve rules | `olistCleanAppr01` | `n8n/cleaning_approval.json` | The approver, through its form URL |

Both files are generated by `python -I scripts/build_cleaning_workflows.py`.

---

## 1. The idea in one picture

```
raw.<table> ──copy──▶ cleaning.<table> ──profile (SQL)──▶ Cleaning agent ──rules (JSON)──▶ Check rules
                                                                                         │
                       ┌──────────── safe: applied automatically ◀───────────────────────┤ fixed policy,
                       │                                                                 │ not the AI
                       │           risky: n8n Form ──approve / reject──▶ ops.cleaning_rules
                       ▼                                                                 │
              one SQL transaction per table: rebuild copy → apply rules → cast types ──▶ clean.<table>
                                                                                  └─────▶ ops.quarantine
```

Three things keep this reliable:

1. **The AI never writes SQL.** It picks from a fixed list of rule types (`trim`, `parse_date`, `dedupe_key` …) and fills in settings. A Code node turns each rule into SQL from a template, and every value the agent gives (column names, numbers, patterns) is checked before it is used.
2. **The AI doesn't decide what is safe.** A fixed policy in *Check rules* does that. Anything that deletes rows that aren't exact copies, changes what a value means, or reads dates, goes to a person. So does any rule the agent gives a confidence below 0.8.
3. **Postgres does the work.** n8n never pulls the 1M geolocation rows into memory. It moves profiles, rules and decisions around, and each table is cleaned by one SQL script that runs as a single transaction.

## 2. One run, step by step

### 2.1 Propose (per table)

| Step | Node | What happens |
|---|---|---|
| 1 | `Get stored rules` → `Decide` | If the table already has rules, they are reused: no AI call and no new approval. Set `FRESH_RULES = true` in `Tables` to ask again. |
| 2 | `Build working copy` | `raw.<table>` is copied into `cleaning.<table>`, all text, with a row number `_row` in load order. Raw is never changed. |
| 3 | `Profile columns`, `Profile table` | FR-K1. Per column: blanks, placeholder words, spaces, case, accents, number range, the most common **value shapes** (`99/99/9999 99:99`, `A$ 99,99` …), common values and values written several ways. Per table: blank rows, header rows, exact duplicates, duplicate keys, the keys seen in `raw_record`, and the extra checks from `Tables`. Tables over 200,000 rows use a repeatable sample for the column part. |
| 4 | `Cleaning agent` | FR-K2. Gets the profile, the target column types and the collection stage's data contract. Returns a list of rules in fixed JSON. |
| 5 | `Check rules` | Validates, sorts into the fixed run order, classifies safe / risky (FR-K3), and builds the SQL. |
| 6 | `Dry run rules` | Runs all valid rules on the working copy to count rows affected and keep 3 before → after examples per rule. |
| 7 | `Save rules` | Every rule goes into `ops.cleaning_rules` with status `auto` (safe), `pending` (risky) or `invalid` (never runs). |

### 2.2 Approve

If any rule is `pending`, the run writes an `awaiting_approval` row to `ops.agent_logs` with the form link, and **pauses** at `Wait for approval` (FR-K4).

The approver opens **http://localhost:5678/form/olist-cleaning-approval**, enters their name, and gets one page with every risky rule: what it does, rows affected, examples, and why it needs approval. They choose Approve or Reject for each one. Submitting saves the decisions and wakes the paused run.

If nobody answers within **2 hours**, the run continues anyway, and undecided rules become `expired` (treated as rejected).

### 2.3 Apply (per table)

`Build cleaning SQL` makes one script per table, and `Run cleaning SQL` runs it as one transaction (FR-K5):

1. Rebuild `cleaning.<table>` from raw.
2. Apply the rules in order:
   - `auto` and `approved` rules run as proposed.
   - For `rejected` and `expired` rules, the values the rule would have fixed **become null**. Rows a rejected rule would have deleted **stay**.
3. Cast every column to its type. Values that still don't fit become null and are counted (`cast_failures` in the log).
4. Rows with a missing or repeated key go to `ops.quarantine`, along with rows deleted by `drop_rows_matching` and `dedupe_key`. Exact duplicates and blank rows are not kept there, since nothing is lost.
5. Replace `clean.<table>`. If anything fails, the transaction rolls back and the table keeps its previous content.

### 2.4 Log

FR-K6. Everything is in `ops.agent_logs` (`agent = 'cleaning'`): one row per proposal, per rule applied (rows changed and the decision behind it), per table (before and after counts), the approval, and a final `run_complete` row with cross-table checks.

## 3. Rule types

Rules always run in this order, whatever order the agent lists them in.

| Order | Rule | Example | Policy |
|---|---|---|---|
| 0 | `rename_key` | `payment_value` ← `raw_record ->> 'paymentValue'` | risky |
| 1 | `drop_blank_rows`, `drop_header_rows` | empty rows, repeated header lines | safe |
| 1 | `drop_rows_matching` | `order_id ~ '^test_order_'` | risky |
| 2 | `dedupe_exact` | exact copies | safe |
| 3 | `trim`, `null_words` | `' sao paulo '`, `N/A`, `NULL` | safe |
| 4 | `change_case`, `remove_accents` | `SAO PAULO` → `sao paulo`, `São` → `Sao` | safe |
| 5 | `map_values` | `deliverd` → `delivered`, `Sao Paulo` → `SP` | safe only if the values differ just in case, accents, spaces, `_` or `-`; otherwise risky |
| 6 | `scale` | `0.25 kg` → `250` | risky |
| 7 | `strip_text` | `R$ 81,16` → `81,16`, `3x` → `3` | safe when the pattern is anchored (`^` / `$`) |
| 7 | `replace_text` | `beleza-saude` → `beleza_saude` | risky |
| 8 | `decimal_comma`, `words_to_numbers` | `81,16` → `81.16`, `two` → `2` | safe |
| 9 | `lpad` | zip `1003` → `01003` | safe |
| 10 | `parse_date` | `02/10/2017 10:56` → `2017-10-02 10:56:00` | **risky** (decided for the demo: day and month could be swapped) |
| 11 | `swap_columns` | lat ↔ lng, purchase ↔ delivery date | risky |
| 12 | `set_value` | negative → positive, 100x price ÷ 100, score 0/6/10 → null | risky |
| 13 | `dedupe_key` | near duplicates with the same key | risky |

Any rule with agent confidence below 0.8 is risky too.

## 4. Setup

1. **Supabase:** run `scripts/clean_tables.sql` once in the SQL editor, after `raw_tables.sql` and `n8n/ops_tables.sql`. It creates the `clean` tables (the table contract), the `cleaning` work area with its helper functions, and `ops.cleaning_rules`, `ops.cleaning_approvals` and `ops.quarantine`. It is safe to run again.
2. **Import** `cleaning_approval.json` and `cleaning_main.json` (n8n stopped, as in section 6 of `n8n/README.md`, or through the editor).
3. **Credentials:**

   | Workflow | Postgres (`Supabase`) | Gemini (LLM) |
   |---|---|---|
   | Cleaning · Main | every Postgres node (Get stored rules, Build working copy, Profile columns, Profile table, Get contract, Dry run rules, Save rules, Log proposal, Log reuse, Count pending rules, Save approval request, Log waiting, Expire undecided rules, Get rules to apply, Run cleaning SQL, Log cleaning, Check clean tables, Log run) | Cleaning model |
   | Cleaning · Approve rules | Get pending rules, Save decisions, Log approval | – |

4. **Publish `Cleaning · Approve rules`.** Its form only answers at the production URL when the workflow is published.
5. **Run:**
   1. Run the collection stage first.
   2. In `Cleaning · Main` → `Tables`, set `ONLY = ['sellers']` and click *Execute workflow*.
   3. Open the form link from the `Log waiting` row, decide, and the run continues.
   4. Then run with `ONLY = []`.

Quick checks:

```sql
-- what happened in the last run
select action, source, status, rows_read, rows_written, reason
from ops.agent_logs where agent = 'cleaning' order by logged_at desc limit 40;

-- every rule and its decision
select source, rule_order, rule_type, column_name, risk, status, rows_affected, decided_by
from ops.cleaning_rules order by source, rule_order;
```

## 5. Table contract (clean schema)

Same table and column names as the original Olist files, typed. It's defined in `scripts/clean_tables.sql` and repeated in the `Tables` node (keep both the same).

| Table | Key | Typed columns |
|---|---|---|
| `clean.orders` | order_id | 5 timestamps |
| `clean.order_items` | order_id, order_item_id | order_item_id integer, shipping_limit_date timestamp, price and freight_value numeric(12,2) |
| `clean.customers` | customer_id | all text (zip prefix stays text, 5 digits) |
| `clean.sellers` | seller_id | all text |
| `clean.geolocation` | none (a zip prefix has many points) | lat, lng double precision |
| `clean.products` | product_id | 7 integers (weight in grams) |
| `clean.category_translation` | product_category_name | all text |
| `clean.payments` | order_id, payment_sequential | sequential, installments integer, value numeric(12,2) |
| `clean.reviews` | review_id, order_id | score smallint, 2 timestamps |

`review_id` alone is not unique in the original data (789 repeats), so the key for reviews is `(review_id, order_id)`.

## 6. Things to watch

- **Re-runs are cheap:** after the first run, the stored rules are reused, so there's no AI call and no form. For the live demo, set `FRESH_RULES = true` (or `ONLY` to one table) to show the agent and the approval again.
- **Rejected means null:** rejecting `parse_date` on `order_purchase_timestamp` leaves about 14,000 purchase dates empty. That is deliberate (bad values are not passed on), but explain it to the approver.
- **Speed:** profiling and cleaning run inside Postgres. Geolocation (1M rows) is the slowest table; its column profile uses a sample.
- **Keep the contract in sync:** if the data-out track changes a clean table, update both `clean_tables.sql` and the `Tables` node.
- **`ops.quarantine` keeps only the latest run** for each table.
